# Recipig

Personal recipe app: import a recipe from a URL (recipe only, no blog fluff), save it, edit it, tick off ingredients as purchased, and expand per-step ingredient reminders.

## Stack

- `backend/`: Node 22, Express 5, TypeScript run with `tsx`, cheerio for HTML parsing. Storage is MongoDB (`mongodb` driver); users log in with username + password.
- `frontend/`: Angular 20, standalone components, signals, inline templates, one global stylesheet (`src/styles.css`). Dev server proxies `/api` to `127.0.0.1:3000`.

## Commands

- Backend: `cd backend && npm install && npm run dev` (API on :3000; needs MongoDB, see README), `npm test` (add `TEST_MONGODB_URI=...` to run the Mongo store tests), `npm run typecheck`, `npm run import-json -- <username>` (moves an old `recipes.json` into an account), `npm run refresh-images -- [--dry-run]` (re-reads each recipe's source page and swaps in the sharper version of its photo; set `MONGODB_URI` to run it against Atlas)
- Frontend: `cd frontend && npm install && npm start` (:4200), `npm run build` (output `dist/frontend/browser`, which the backend serves when present)

## Conventions

- Backend imports use explicit `.ts` extensions (`allowImportingTsExtensions`). Avoid TS syntax Node can't strip natively (parameter properties, enums, namespaces) so the dependency-free tests also run with plain `node --test`.
- Accounts: `POST /api/auth/register|login|logout`, `GET /api/auth/me`. Passwords are scrypt hashes (`password.ts`). A login is a random token in an httpOnly SameSite=Lax cookie (`recipig_session`); only its SHA-256 hash is stored in `sessions`. Every `/api/recipes*` route requires a user and every store call takes the `userId`; another user's recipe is a 404, never a 403. Don't add a recipe path that skips `userId`. Storage is behind the interfaces in `stores.ts`: `mongoStores.ts` for real, `memoryStores.ts` for tests; both must pass `test/storeContract.ts`.
- API: `GET/POST /api/recipes`, `POST /api/recipes/import {url}`, `POST /api/recipes/import-photos {photos}`, `GET/PUT/DELETE /api/recipes/:id`, `GET/POST /api/sources`, `PUT/DELETE /api/sources/:id`, `POST /api/images` (raw image body), `GET /api/images/:id`. All input to POST (create) and PUT goes through `parseRecipeInput` (`backend/src/validate.ts`).
- Ingredients and steps each have an optional `section` label. The UI groups consecutive items with the same label; the key is omitted (not empty) when there is none. A single label shared by every item is dropped on import because it divides nothing. Step linking uses the step's section to break ties between same-named ingredients.
- Frontend: `RecipeEdit` is both the edit form (`/recipes/:id/edit`) and the blank-recipe form (`/recipes/new`, route data `{ mode: 'create' }`). The header "New Recipe" menu (in `app.ts`) links to `/recipes/new` and opens `ImportDialog` (`import-dialog.ts`, a `<dialog>`; there is no import page). A recipe has optional `notes` (the cook's own tweaks and ideas for next time), edited in `RecipeEdit` and shown on the recipe page as a Notes card between the recipe details and the batch size / Ingredients, only when not blank. Steps briefly had their own notes; `foldStepNotes` (`backend/src/stores.ts`) moves any such leftovers into the recipe notes whenever a recipe is read, and saving makes it permanent.
- Look and feel: three themes, picked per account from the header's account menu (Change theme): Friendly (default; cosy pastel "village", Animal Crossing-ish, polka-dot meadow), Aurora (starry night sky, cards fading from bright aurora colours to clear; the stars are one non-repeating image, `frontend/public/backgrounds/starfield.svg`, generated by `frontend/scripts/make-starfield.mjs` with a fixed seed: edit and rerun the script rather than the SVG) and Terminal (monospace, green-on-dark, outlined cards; a quiet editor with underlined fields). An account whose saved theme no longer exists gets the default. Every colour, font, border width, corner radius and shadow is a token in the first block of `frontend/src/styles.css` (Friendly); the other `[data-theme='…']` blocks override tokens only, so the theme picker's previews (elements with their own `data-theme`) render each theme. Use tokens rather than literal colours or sizes in components; the few theme-specific chrome rules sit at the end of the file. The theme is `data-theme` on `<html>`, set by `ThemeService` (`theme.service.ts`), saved on the account (`PUT /api/auth/theme`, `theme` on `/api/auth/me`; `THEMES` in `backend/src/stores.ts` and `theme.service.ts` must match) and cached in localStorage (`recipig-theme`), which an inline script in `index.html` applies before Angular starts. The picker also has "Hide recipe photos in <theme>", a per-theme choice saved on the account (`hideImagesIn` on `/api/auth/me`, `PUT /api/auth/hide-images {themes}`; an account that has never set it gets `DEFAULT_HIDE_IMAGES_IN`, Terminal only, for its text-only look); when the current theme is in that list `ThemeService` sets `data-hide-images` on `<html>` and `styles.css` hides the card thumbnails and the recipe page photo (not the editor's preview). Fonts (Fredoka, Nunito, Google Sans Code) load from Google Fonts in `index.html` with system fallbacks. Keep text contrast readable on every tile in every theme, and keep animations behind the reduced-motion rule.
- Batch size (0.5x-4x) is display-only: `RecipeDetail` keeps a `multiplier` signal and shows `scaleIngredientText(text, factor)` from `frontend/src/app/scale.ts`; the stored recipe is never rewritten. `scale.ts` must stay free of imports and TypeScript-only syntax so `scale.test.ts` runs under plain `node --test` (and `npm test` in `frontend/`, which uses tsx). Add a test case for any ingredient line that scales wrongly.
- `frontend/src/app/auth.util.ts` (`safeReturnUrl`, stops open redirects after login) is import-free like `scale.ts`, so `auth.util.test.ts` runs under plain `node --test`. The login/create-account page is `auth-page.ts` (route data `{ mode: 'register' }`); `authGuard`/`guestGuard` protect routes and `authInterceptor` sends any 401 outside `/api/auth/` to `/login`.
- Tags: a fixed list of main-ingredient tags (`Poultry`, `Beef`, `Pork`, `Fish`, `Vegetarian`) in `RECIPE_TAGS`, defined in both `backend/src/tags.ts` and `frontend/src/app/models.ts` (keep them in sync). `recipe.tags` is omitted when empty; `parseRecipeInput` rejects unknown tags and stores them in list order. `detectTags` guesses them at import (a meat in the title wins, then the ingredients; Poultry is any bird (chicken, turkey, duck, goose, quail, game hens...); stock, fat, duck sauce, eggs, fish sauce and anchovies don't count as a main ingredient but do rule out Vegetarian); add a `tags.test.ts` case for any recipe it gets wrong. Poultry was called `Chicken` until October 2026: `canonicalTag` still accepts "Chicken" and `renameOldTags` (`stores.ts`) reads saved `Chicken` tags as Poultry; saving makes it permanent. The list page filters by tag (any match, kept in `?tag=` query params) and has a search box (`?q=`): `searchRecipes` (`frontend/src/app/search.ts`, import-free like `scale.ts`, tested in `search.test.ts`) returns name matches first, then ingredient matches with the lines that matched (shown as one grid, each card labelled "Recipe match" or "Ingredient match"); every query word must match at the start of a word, ignoring case, accents and simple plurals, and search works within the tag filter; the editor has toggle pills. Tag icons are MingCute line SVGs in `frontend/public/tag-icons/` (Apache 2.0, see its README), applied as CSS masks per `data-tag` in `styles.css`; to change one, replace its SVG file.
- Nutrition: `RecipeDetail` shows an estimate computed in the browser by `estimateNutrition` (`frontend/src/app/nutrition.ts`) from the ingredient lines and the `FOODS` table (`nutrition-data.ts`, per-100 g values based on USDA FoodData Central, grams per cup / per item / per unit). Nothing is stored; the batch size multiplies the total and per serving divides by the servings number. Lines with no amount or an unknown food are listed as "Not counted", never guessed. Both files are import-free like `scale.ts`; add a `nutrition.test.ts` case for any line that is read wrongly, and add foods to the table as needed (the longest matching name wins).
- Recipe photo on import (`pickImage` in `extract.ts`): only the recipe's own structured-data `image` (the finished dish; step photos are never considered), and only versions of its first photo (the same file at another `-WxH` size, crops with stated width/height, or the same file as `og:image`). The largest landscape crop at least 1000px wide wins, else the full-size original, else the largest. `recipePhoto` exposes the same choice for `scripts/refreshImages.ts`, which only replaces a saved photo the page itself offers.
- Import from photos: New Recipe → From Photos opens `PhotoImportDialog` (`photo-import-dialog.ts`): up to 6 photos in page order, shrunk to a 2400px JPEG in the browser and sent as base64. `POST /api/recipes/import-photos` (its own 15mb JSON limit, parsed only after the login check; every other route keeps 1mb) asks Claude (`backend/src/photoImport.ts`: `claude-opus-5-5`, structured output via a Zod schema, server-side refusal fallbacks on) and returns an unsaved draft built by `buildDraft` (`extract.ts`, shared with URL import: ids, step links, tags). The frontend passes the draft to `/recipes/new` in the navigation state, and `RecipeEdit` shows it with a "check it against the book" notice. Photos are never stored. Per-account limit 30 a day (in memory). Without `ANTHROPIC_API_KEY` the endpoint answers 503; tests pass a fake `readPhotos` in `AppOptions` and never call Claude.
- Sources: each account keeps its own list of sources (a cookbook, "NY Times", a person), each a name (unique per account, ignoring case, up to 60 characters) and an icon (`backend/src/sources.ts`; `SourceStore` in `stores.ts`, Mongo collection `sources`). A recipe has at most one, as `sourceId`; `POST`/`PUT /api/recipes` reject a source id the user doesn't own, and deleting a source unsets it on that user's recipes (`clearSource`). This is separate from `sourceUrl`, the page a recipe was imported from, which the editor shows as an editable Link and the recipe page links by host name. Icons: `SOURCE_ICONS` in `backend/src/sources.ts` and `frontend/src/app/models.ts` (keep in sync) name MingCute line SVGs in `frontend/public/source-icons/` (see its README); the pill gets its icon from an inline `--tag-icon` style and its colour from `.tag-pill.source-pill` (`--lilac`). The account menu's Sources opens `SourcesDialog` (list, add, edit, delete); the editor has a Source dropdown and "+ New source" (`openNew()`, which selects what it creates). Cards show the source icon after the tag icons; the recipe page shows it as a pill after the tags; the list filter has source pills after the tag pills (`?source=<id>`): a recipe must match any picked tag and any picked source. `SourceService` caches the list per login. A short-lived free-text `source` field (October 2026) is moved into the notes as "Source: ..." when read (`foldSourceText`).
- Uploaded recipe photos: the editor's Photo field has Upload/Change/Remove (plus "Or an image link" when the photo isn't an upload). `shrinkPhoto` (`image-resize.ts`, shared with photo import) makes a JPEG of at most 1600px, sent as the raw body of `POST /api/images` (`express.raw`, 4 MB limit, JPEG/PNG/WebP checked by their first bytes; 100 uploads a day per account). Images live in the database (`ImageStore`, Mongo collection `images`; Render's disk doesn't persist) and are served only to their owner at `/api/images/<id>`, with a long private cache since an id never changes. A recipe's `image` is an http(s) link or such a path (`optionalImage` in `validate.ts`). Changing or removing a recipe's uploaded photo, or deleting the recipe, deletes the image unless another recipe uses it; each upload also sweeps that user's uploads no recipe uses that are over a day old (an editor left without saving).
- Step-to-ingredient links are stored on each step as `ingredientIds` and are auto-detected at import (`backend/src/link.ts`); the editor lets the user correct them.
- Hosting: `render.yaml` is a Render Blueprint (one Node web service: build the frontend, `npm ci --include=dev` in both folders because `tsx` and the Angular CLI are dev dependencies, start the backend). Production sets `HOST=0.0.0.0`, `COOKIE_SECURE=true`, `TRUST_PROXY=1`; `MONGODB_URI` (Atlas), `SIGNUP_CODE` and `ANTHROPIC_API_KEY` are secrets set in Render. With `SIGNUP_CODE` set, `/api/auth/register` needs a matching `inviteCode` (compared in constant time, attempts count toward the sign-up rate limit) and `GET /api/auth/signup` tells the form to ask for it.
- The importer fetches user-supplied URLs, so `fetchPage.ts` must keep refusing private/loopback addresses on every redirect hop. The server binds to localhost by default for the same reason.

## Status

- Live on Render (Blueprint in `render.yaml`) with MongoDB Atlas; the owner uses it day to day.
- Verified on 2026-10-21: backend `npm test` with `TEST_MONGODB_URI` set (76 tests, including the Mongo store contract and the Express/auth `app` tests), `npm run typecheck`, frontend `npm test` (29) and the same files under plain `node --test`, and `ng build`. Render's build and start commands were also run from a clean copy with production settings.
- Seen in a browser: recipe list (tags, filter, cards), recipe page (meta pills, batch size, nutrition), the editor's tag toggles, login/sign-up (invite code), header at desktop and phone widths.
- From Photos (2026-10-28): run end to end in a browser against a local stand-in for the Claude API (pick, reorder, read, editor prefill, save with tags, sections and step links). Not yet run against the real API, and the dialog's look wasn't checked in screenshots.
- Not yet looked at in a browser: the editor's ingredient reorder buttons, image-link preview and section tags in the step ingredient picker (they build and type-check).
- Nutrition values were written from USDA reference figures; only flour, butter, whole milk and 85% ground beef were checked against the live FoodData Central API (DEMO_KEY rate limits stopped the rest). Treat other rows as approximate and correct them when a recipe looks off.
- Running a preview server from a tool: use its own port (e.g. 3100) and database, and stopping the background task does not stop its `tsx` child process. Stop it by the PID listening on that port only. Never kill Node processes by matching command lines: the owner's `npm run dev` runs the same `src/index.ts`, and the server under `tsx watch` has no "watch" in its command line.
- Both `package-lock.json` files are committed; commit lockfile changes along with any dependency change.
